Build a production-ready Configuration page inside the System Admin Panel for a multilingual AI translation SaaS.

Goal:
Create an admin-only control center where platform administrators can add, test, activate, deactivate, and route LLM providers/models. The system must intelligently choose the best available model based on:
1) subject matter/domain
2) language pair
3) region
4) content length / context size
5) content type
6) priority (quality / speed / cost)
7) model availability and fallback status

Important architectural rule:
Do NOT hardcode model choices directly into business logic.
Instead, create a flexible rules engine + admin UI so the operations team can update routing logic without code changes when providers deprecate models or new models outperform old ones.

Context:
This platform serves enterprise customers, agencies, and possibly sub-clients. Translation quality must be optimized by using the most relevant LLM for the specific language pair and subject matter.

Current strategy assumptions to support as INITIAL ADMIN-EDITABLE defaults:
- Technical / legal / medical / specialized documentation:
  prefer high-reasoning, high-control models
- Creative / literary / marketing translation:
  prefer models known for tone, nuance, and style
- Very large documents:
  prefer long-context models
- Major European language pairs:
  several flagship models may be valid
- Asian language pairs:
  support regional/specialized providers where configured
- Low-resource languages:
  support multilingual/research-focused models where configured

But these must be fully editable in admin settings.

Build the page and supporting backend with the following scope:

==================================================
6. ROUTING RULES ENGINE
==================================================

This is the most important part.

Build a configurable rules engine with rule priority ordering.

A rule can route based on any combination of:
- source language
- target language
- language pair
- source region
- target region
- subject matter/domain
- content type
- token/document size
- customer tier
- workspace type (direct client / agency / reseller / enterprise)
- requested output style
- terminology strictness
- speed-vs-quality preference
- data residency requirement
- provider availability
- budget limit
- human review required? yes/no

Each rule should support:
- Rule name
- Description
- Priority number
- Enabled toggle
- Match conditions
- Primary model
- Secondary fallback
- Tertiary fallback
- Confidence threshold
- Terminology mode
- Glossary enforcement mode
- Style guide mode
- Retry behavior
- Timeout behavior
- Escalation behavior
- Notes

Rule logic behavior:
- Highest priority matching rule wins
- If primary model unavailable, use fallback chain
- If no exact rule match exists, use a default global routing policy
- Admin can reorder rules via drag-and-drop
- Admin can simulate a request and see which rule matched and why

14. ROUTING ENGINE IMPLEMENTATION NOTES
==================================================

Implement a scoring + rule-priority system:
- exact language pair match > language family match
- exact domain match > broad domain tag match
- approved/production models only by default
- deprecated/retired models excluded unless explicitly forced
- disabled models never selectable
- long-document requirement must check context capacity
- low-resource language requests should boost multilingual/research-focused models
- premium-quality mode favors quality tier
- cost-sensitive mode favors lower cost tier
- speed mode favors low latency tier

Support a final “policy guardrail” layer:
- reject models that do not meet data residency policy
- reject models that do not support required features
- reject models that exceed configured cost thresholds
- reject models that are unhealthy or unavailable
