FIX 3 — Verify and fix the context window to be a true sliding window, not chunking
The current implementation is described as a ±2 segment context window. This could be implemented as either a sliding window (correct) or non-overlapping chunks of 5 (wrong). These look similar but produce very different translation quality. Segments at chunk boundaries get no context on one side with chunking, which is exactly the problem we were solving.
Verify this now by answering: for a 10-segment document, which context segments does segment #5 receive when the AI call is made for it?
The correct answer is: [seg3, seg4] before and [seg6, seg7] after — meaning a fresh window is built for every single anchor segment, and the anchor increments by 1 each iteration.
If the current implementation groups segments into non-overlapping batches of 5 instead, fix lib/ai-translate.ts as follows:
for anchorIndex from 0 to segments.length - 1:
  contextBefore = segments[max(0, anchorIndex - 2) : anchorIndex]
  contextAfter  = segments[anchorIndex + 1 : min(length, anchorIndex + 3)]
  anchor        = segments[anchorIndex]
  → build prompt with [CONTEXT] tags for before/after, [TARGET] tag for anchor
  → make single LLM call
  → write result back to anchor segment only
Edge cases that must be correct:

Segment 0: 0 context segments before, 2 after — pad with [CONTEXT-EMPTY] on left
Segment 1: 1 context segment before, 2 after
Second-to-last segment: 2 before, 1 after
Last segment: 2 before, 0 after — pad with [CONTEXT-EMPTY] on right
Table cells: context window restricted to cells with the same tableId — never mix table cells with body paragraph context
blockType = "header" or "footer": translated independently with no context window at all
DNT glossary exact match: source text copied verbatim as translation, no LLM call, no context window built

Show the loop structure in the updated code after the fix.

FIX 4 — Fix bounding box redaction to sample background color, not use hardcoded white
In services/pdf-processor/app.py, in the /apply-overlay endpoint, show exactly how bounding box redaction is performed before the translated text is inserted.
If the current implementation paints the bbox with a hardcoded color (white (1,1,1), black, or any fixed value), fix it immediately. Hardcoded white leaves visible white rectangles on colored backgrounds, dark-themed PDFs, or any document with a non-white page background — a visually obvious defect on any branded document.
Fix it as follows:

Before redacting a bbox, rasterize a 10px border region around the bbox on that page using PyMuPDF's get_pixmap() with a clip rect slightly larger than the bbox
Compute the median RGB value of the pixels in that border strip
Use that median color as the fill color for the redaction rectangle
Then insert the translated text on top at the exact bbox coordinates

If the bbox is on a white page (median RGB ≥ 245, 245, 245), white fill is fine — the sampling result will confirm it. The fix only matters for non-white backgrounds.

FIX 5 — Verify multi-column reading order uses column band detection, not global y-sort
In services/pdf-processor/app.py, in the /extract endpoint, show the reading order assignment logic.
A naive global y-coordinate sort on a two-column PDF will interleave left and right column text — for example, the first line of column 2 will appear in reading order between the first and second lines of column 1. This produces completely wrong segment ordering, which breaks both the context window logic and the final document assembly.
The correct behavior: for a two-column document, all left-column blocks must appear before all right-column blocks in readingOrder.
Verify by describing what readingOrder values would be assigned to a page with 4 blocks: left-column blocks at x=72 and x=72 (y=100 and y=200), right-column blocks at x=320 and x=320 (y=100 and y=200). The correct answer is readingOrder 0, 1, 2, 3 assigned as: left-col y=100, left-col y=200, right-col y=100, right-col y=200.
If the current implementation does a global y-sort (which would give: left y=100, right y=100, left y=200, right y=200), fix it as follows:

After extracting all blocks for a page, compute the page's median x-coordinate of all block left edges
Cluster blocks into columns: blocks whose left edge is within 30% of page width of each other belong to the same column
Sort columns left to right by their median x-position
Within each column, sort blocks top to bottom by their bbox.y
Assign readingOrder sequentially across columns: all blocks in column 1 first, then all blocks in column 2, etc.
For pages with 3+ columns, the same rule applies — sort columns by x, assign readingOrder column-by-column
